# Edit surface guard

Objective: block a `write` worker launch whose spec lacks a valid `## Allowed edit surfaces` section, in code, before the launch runs. Branch: `feature/edit-surface-guard`. Delivery: `ask-on-risk`. Runner: `bash tests/run.sh`.
Profile: `claude-gpt`.

## Specs

- S1 (user, verbatim): "procede con el hook de superficie de edición", accepting the parent's proposal (verbatim): "controlar la superficie de edición en código, con un hook `PreToolUse` que valide `## Allowed edit surfaces` antes de lanzar un writer."
- S2 (source of the idea, from the gentle-shell comparison): gentle-shell parses the section and blocks malformed or unscoped writer launches in code (`lib/bounded-writer-admission.ts`, `rejectUnscopedBoundedWriterDispatch`); odd-flow says "This is a prompt rule: nothing enforces it at write time" (`skills/odd-flow/references/delegation.md:31`).
- S3 (assumption): the guard is a Claude Code `PreToolUse` hook in `hooks/hooks.json` with matcher `Agent|Task|Bash`, running `scripts/pre-tool-use.py`. It applies in both orchestrator modes.
- S4 (assumption): a launch is a writer launch when its spec's first non-empty line is `# Role: write` (the `assets/spec-template.md` heading). Specs come from: the `Agent`/`Task` tool's `tool_input.prompt`; and, in a `Bash` command, every `orchestration task-create` or `orchestration worker-start` invocation, through `--spec-file <path>`, `--spec-file=<path>`, `--spec <text>` or `--spec=<text>`. One Bash command may hold several launches (parallel start); each is checked. A `worker-start --task <id>` without a spec is not checked (its spec was checked at `task-create`).
- S5 (assumption): validation follows `delegation.md` (Allowed edit surfaces): the exact heading `## Allowed edit surfaces`; the section ends at the next Markdown heading; every non-empty line is one entry (a leading `- ` or `* ` bullet and surrounding backticks are stripped). Rejected: a missing or empty section; `.`, `./`, `/`, any absolute path, `~` paths, any `..` segment; an entry whose first path segment contains a wildcard (`*`, `**/*`, `*.py`); an unfilled template placeholder (`<...>`). Each rejection names the entry and the rule.
- S6 (assumption): a launch whose writer status cannot be determined is blocked with a fix hint: a `--spec-file` argument that is not a literal path (contains `$`, a backtick or a glob), a spec file that does not exist or cannot be read, or an orchestration launch whose arguments cannot be parsed. `orca-dispatch.md` tells the parent to pass a literal spec path.
- S7 (assumption): a block uses the documented PreToolUse JSON (`hookSpecificOutput.permissionDecision: "deny"` with `permissionDecisionReason`). An allowed call prints nothing and exits 0; the hook never prints `"allow"`, so the normal permission flow always applies. An internal error never blocks an unrelated tool call; a Bash command without `orchestration` and an Agent prompt without `# Role: write` return before any spec parsing.
- S8 (assumption): the parser lives in `skills/odd-flow/scripts/surface.py`, with a CLI `surface.py check <spec-file>` (exit 0 and the entries on stdout when valid, exit 2 and the reason on stderr otherwise), so runtimes without Claude Code hooks can call it. The hook reuses it.
- S9 (assumption): the guard checks the section's presence and shape at launch, not what the writer edits afterwards; the parent's post-return `git diff --name-only` comparison stays. `delegation.md`, `orca-dispatch.md`, `README.md`, `NOTES.md` and the `hooks/hooks.json` description say so.
